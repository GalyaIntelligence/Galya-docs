The model is promptable, and a schema is its prompt: the questions it answers about each item, each with a fixed set of options. Every item and user call names one. Start from a [default schema](/guides/schema-library) for your domain, extend it with your own questions, or write your own from scratch.

## Default schemas

The [schema library](/guides/schema-library) has a default schema for fashion and apparel, travel, hospitality, tech and electronics, watches, trading cards and video games. Use one by id or inline, or copy it and change the questions.

## Your own questions

A question has an `id`, the question `text` and 2 to 24 `options`. The model answers it per item as the field `q:<id>`. Write questions the way you would ask a merchandiser who can see the product.

```json
{
  "name": "occasion-and-fit",
  "base": "galya-commerce-v3",
  "questions": [
    { "id": "occasion", "text": "What occasion is this product for?", "options": ["Work", "Party", "Everyday"] },
    { "id": "fit", "text": "How does it fit?", "options": ["Slim", "Regular", "Relaxed"] }
  ]
}
```

- `base` includes another schema's fields as well (here the 219 fields of `galya-commerce-v3`); `base: null` uses only your questions.
- Up to 64 questions per schema.
- Read a few items' readouts (`GET /v1/item/{itemId}?schema=...`) to see how the model answers a new question, and tune the wording or options.

<Tip>
  Keep schemas in your code and send the definition inline as `schema` on `/v1/item` and `/v1/user`. Galya stores it the first time and returns its id as `schema_id`. You never have to call this endpoint.
</Tip>

## Ids are content hashes

A schema's id is `sch_` plus a hash of its `base` and `questions` (`name` is only a label). So:

- The same definition always gets the same id, and posting it again returns `200` with that id.
- Schemas are immutable. Changing a question makes a new schema; the old one and its readouts stay usable.
- There is no limit on how many a workspace has.

<RequestExample>

```bash
curl https://api.galya.io/v1/schemas \
  -H "X-API-Key: $GALYA_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "occasion-and-fit",
    "base": "galya-commerce-v3",
    "questions": [
      { "id": "occasion", "text": "What occasion is this product for?", "options": ["Work", "Party", "Everyday"] }
    ]
  }'
```

</RequestExample>

## Manage schemas

- `GET /v1/schemas` lists every schema the workspace has used or registered, plus `galya-commerce-v3`.
- `GET /v1/schemas/{schemaId}` returns one, with how many items have a readout for it.
- `DELETE /v1/schemas/{schemaId}` removes a schema you created.

## Taste across schemas

Interactions are stored once, without a schema. A user call computes taste through the schema it names, so one shopper's history can be read through a default schema in one call and through your own `q:occasion` question in the next. If items don't have a readout for that schema yet, they are queued and listed under `not_ranked` with `pending`.
